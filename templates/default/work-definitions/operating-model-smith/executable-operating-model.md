# Executable operating model standard

A sound package changes observable behavior rather than merely summarizing a method. Its documents expose recognizable triggers, relevant observations, legitimate choices, failure modes, stopping conditions and authority handoffs.

Keep source doctrine, Airic-specific translation, explicitly approved supplements and later lessons distinguishable. A narrow source may produce a narrow package; do not fill gaps with unattributed generic advice.

Use `work.yml` only for identity, loading, dependencies, domain compatibility and completion evidence. Use Markdown for flexible method and judgment. Include at least two legitimate paths when order or approach is intentionally flexible. Put enforceable business invariants in domain code.

The complete package must have resolvable links, minimal required context, reachable on-demand content, consistent terminology and no capability claim that depends on absent code or unresolved authority.
