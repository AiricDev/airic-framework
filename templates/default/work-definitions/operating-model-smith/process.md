# Onboard an operating model

Turn the user's method, examples and authority boundaries into one coherent `work-definitions/<id>/` package. Treat supplied material as evidence of a method, not permission to invent one.

First establish the work governed, intended users, supported capability, explicit non-goals, source locations and consequential decisions that remain human-owned. Inspect relevant domain code so the method calls real capabilities without restating domain invariants in Markdown.

Decompose the package into the smallest useful set of required and on-demand documents. Work one review unit at a time: explain its responsibility, source support, neighboring boundary and meaningful alternatives before writing it. The user may review quickly, request revision or pause; preserve exact resume state in an optional `_onboarding.md`, which is not listed in `work.yml`.

Both a new package and a correction to an existing package are valid paths. For a new package, establish identity and capability boundary before details. For an existing package, preserve unrelated content and identify the exact behavioral gap before editing.

Before completion, validate every manifest reference, dependency, path, capability claim, stopping condition and authority handoff as one package. Run the approved operating-model check, inspect the Work change set, and report source limits and unresolved decisions. Do not commit the files or publish a separate revision.
